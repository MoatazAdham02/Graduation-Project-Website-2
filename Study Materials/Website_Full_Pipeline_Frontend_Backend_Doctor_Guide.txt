================================================================================
COROnet - FULL WEBSITE PIPELINE (FRONTEND + BACKEND) DOCTOR GUIDE
================================================================================

Purpose:
This document explains the complete end-to-end pipeline of the website, from
user interaction in the browser to backend processing, database persistence, and
response rendering. It is written for deep academic/doctor discussion.


--------------------------------------------------------------------------------
1) SYSTEM-LEVEL ARCHITECTURE
--------------------------------------------------------------------------------

The project uses a 3-layer architecture:

1) Frontend (React + TypeScript + Vite)
- Runs in browser, manages UI and user flow.
- Sends HTTP requests to backend APIs.

2) Backend API
- Primary implementation: Node.js + Express (port 4000 by default).
- Alternative implementation present: FastAPI (Python, port 8000 default).
- Exposes REST endpoints under /api.

3) Data/Storage layer
- MongoDB for users/scans/items.
- Filesystem storage for uploaded DICOM files (uploads/dicom).

Communication style:
- Request/response over HTTP.
- Mostly JSON; DICOM file endpoint returns binary file data.


--------------------------------------------------------------------------------
2) STARTUP PIPELINE (WHAT HAPPENS WHEN EVERYTHING RUNS)
--------------------------------------------------------------------------------

Frontend startup:
1) Browser loads built assets (or Vite dev server assets).
2) main.tsx mounts App.
3) Providers initialize (theme, toast, confirm, auth).
4) AuthContext checks stored token and validates via /api/auth/me.
5) Router resolves route and renders page.

Backend startup (Express):
1) Load environment variables from Backend/.env.
2) Create Express app.
3) Configure CORS + JSON body parser.
4) Register health/auth/scan/items route modules.
5) Connect to MongoDB.
6) Begin listening on configured port.

Backend startup (FastAPI alternative):
1) Load settings from env.
2) Initialize FastAPI app + CORS.
3) Initialize Mongo client lifecycle.
4) Register routers.
5) Run with uvicorn.


--------------------------------------------------------------------------------
3) AUTH PIPELINE (REGISTER -> LOGIN -> SESSION -> PROTECTED ACCESS)
--------------------------------------------------------------------------------

Register flow:
Frontend:
- Signup page submits name/email/password to POST /api/auth/register.

Backend (Express):
- Validate input (required fields + password length).
- Normalize email.
- Check for duplicate user.
- Hash password (bcrypt pre-save hook in User model).
- Create user document in MongoDB.
- Sign JWT token using JWT_SECRET.
- Return token + public user object.

Frontend:
- Store token in localStorage (coronet-token).
- Store user in AuthContext state.
- User can access /app routes.

Login flow:
Frontend:
- Login page sends credentials to POST /api/auth/login.

Backend:
- Find user by email.
- Compare password with hash.
- Return JWT + user data on success.

Session restore flow:
Frontend:
- On reload, read token and call GET /api/auth/me with Bearer token.

Backend:
- authMiddleware verifies JWT.
- Loads user from DB.
- Returns user if valid; 401 if invalid/expired.

Protected route flow:
- ProtectedLayout blocks /app if no valid user in context.
- Redirects unauthenticated users to /login.


--------------------------------------------------------------------------------
4) DICOM UPLOAD PIPELINE (END-TO-END CRITICAL PATH)
--------------------------------------------------------------------------------

Step A - Client selection:
- User selects or drags DICOM file(s) in UploadScan/Compare.
- Frontend prepares FormData with field name "file".
- Optional metadata fields included: patientName, studyDate, modality.

Step B - HTTP request:
- POST /api/scan/upload
- Headers managed automatically for multipart/form-data by browser.
- Authorization Bearer token is included because scan routes are protected in
  current Express code.

Step C - Backend validation (Express):
- authMiddleware validates user token and attaches req.user.
- Multer validates file type (.dcm/.dicom or application/dicom).
- Multer enforces max file size (500 MB).
- Safe filename generated; file written to uploads/dicom.

Step D - Duplicate policy:
- Backend checks existing scan by same user + filename + studyDate (+ patient).
- If duplicate: returns 201 with skipped=true and reason.

Step E - Persistence:
- Create scan document in MongoDB including:
  userId, doctorName, originalName, path, size, mimeType, patientName,
  studyDate, modality, timestamps.

Step F - API response:
- Returns uploaded scan metadata.
- Frontend updates UI and notifies user.


--------------------------------------------------------------------------------
5) SCAN LIST/DETAIL/FILE/DELETE PIPELINES
--------------------------------------------------------------------------------

List scans:
1) Frontend GET /api/scan with token.
2) Backend filters by req.user._id (user-specific data isolation).
3) Returns summary list sorted by newest first.
4) Frontend renders cards/tables for user.

Get one scan metadata:
1) Frontend GET /api/scan/:id with token.
2) Backend verifies scan belongs to current user.
3) Returns metadata object.

Get scan file:
1) Frontend GET /api/scan/:id/file with token.
2) Backend verifies ownership and resolves absolute file path.
3) Backend blocks path traversal by enforcing path inside UPLOAD_DIR.
4) Backend sends file bytes with appropriate media type.
5) Frontend processes binary content for viewing/parsing.

Delete scan:
1) Frontend DELETE /api/scan/:id with token.
2) Backend verifies ownership.
3) Removes file from disk if present.
4) Removes document from MongoDB.
5) Returns { ok: true }.
6) Frontend refreshes list and confirms deletion.


--------------------------------------------------------------------------------
6) DATA FLOW MODEL (WHAT MOVES WHERE)
--------------------------------------------------------------------------------

Identity data:
- Browser localStorage: token
- Frontend state: user profile
- Database: user document (hashed password, never plaintext)

Medical scan metadata:
- Input form fields from UI
- Saved in MongoDB scan records
- Sent back to frontend in scan APIs

Medical scan file bytes:
- Uploaded from browser to backend using multipart
- Stored on disk under uploads/dicom
- Retrieved by id via controlled file endpoint

Control/feedback data:
- HTTP status codes
- JSON success/error bodies
- Toasts/loading/offline indicators in frontend


--------------------------------------------------------------------------------
7) SECURITY PIPELINE (CURRENT + DISCUSSION POINTS)
--------------------------------------------------------------------------------

Current implemented protections:
- Password hashing with bcrypt.
- JWT authentication for protected routes.
- Scan route authorization by user ownership (Express version).
- CORS allow-list for frontend origins.
- Upload file type/size validation.
- Path traversal prevention before serving files.

Potential weaknesses to discuss honestly:
- Token in localStorage is exposed if XSS occurs.
- No role-based authorization layer shown (admin vs doctor vs user).
- Rate limiting and advanced security headers are not explicitly shown.

Practical next upgrades:
- Move auth to HttpOnly cookie + CSRF strategy.
- Add Helmet/rate limiting/audit logs.
- Add role claims and route-level access policies.


--------------------------------------------------------------------------------
8) ERROR HANDLING PIPELINE
--------------------------------------------------------------------------------

Frontend:
- Handles network errors and non-OK responses.
- Parses text/json safely and shows user-readable messages.

Backend Express:
- Route-level try/catch.
- Global error middleware for consistent JSON errors.
- Special handling for known upload errors (e.g., file too large).

Backend FastAPI:
- HTTPException for controlled failures.
- Exception handler normalizes error payload shape.

Result:
- End users receive stable feedback instead of silent failures.


--------------------------------------------------------------------------------
9) CORS AND ENVIRONMENT PIPELINE
--------------------------------------------------------------------------------

Environment variables:
- Frontend uses VITE_API_URL.
- Backend uses PORT, MONGODB_URI, JWT_SECRET, CORS_ORIGIN, UPLOAD_DIR.

CORS behavior:
- Browser enforces same-origin policy.
- Backend explicitly allows trusted frontend origins.
- Without correct CORS setup, browser blocks requests before app logic runs.

Deployment implication:
- Update env values per environment (dev/staging/production).


--------------------------------------------------------------------------------
10) FASTAPI VS EXPRESS PIPELINE NOTES
--------------------------------------------------------------------------------

Express (Node) is the active full pipeline in current routing usage:
- Auth routes implemented and mounted.
- Scan routes protected with auth middleware and per-user filtering.
- User and scan models are complete.

FastAPI code exists as an alternative backend path:
- Includes health, scan, items modules and auth utilities.
- Useful for future Python/AI-oriented backend expansion.
- In current files, FastAPI main imports auth router that is not present under
  routers/, so FastAPI path may need synchronization before production use.

Discussion strategy:
Present Express as the working implementation and FastAPI as an extensibility
track for ML-centric backend evolution.


--------------------------------------------------------------------------------
11) CLINICAL/ACADEMIC VALUE OF THIS PIPELINE
--------------------------------------------------------------------------------

Why this pipeline is meaningful:
- It models a real medical workflow: secure login -> scan intake -> metadata
  management -> retrieval/comparison/reporting support.
- It separates concerns so each layer can evolve independently.
- It keeps critical decisions on backend trust boundaries (auth, file checks).
- It is practical to demo and still defensible from a software engineering view.

13) POSSIBLE HARD QUESTIONS AND DIRECT ANSWERS
--------------------------------------------------------------------------------

Q: Where is authorization enforced?
A: Backend scan routes in Express require authMiddleware and query by userId, so
   each user accesses only their own scan records.

Q: Why not trust frontend validation only?
A: Frontend can be bypassed. Backend is the trust boundary and performs final
   validation and authorization.

Q: How do you prevent someone downloading arbitrary server files?
A: File endpoint resolves absolute path and confirms it remains inside upload
   directory before sending. Invalid paths are rejected.

Q: What if database is down?
A: Health endpoint reports DB status; operational endpoints fail safely with JSON
   errors, and frontend surfaces readable failure messages.

Q: Is this production-ready?
A: It is a strong graduation-level architecture; production hardening would add
   stronger auth transport, rate limiting, monitoring, role-based access, and
   CI-backed testing.


--------------------------------------------------------------------------------
14) ONE-MINUTE FULL PIPELINE SUMMARY
--------------------------------------------------------------------------------

The website pipeline starts in a React frontend where authenticated users perform
medical workflow actions. Requests go to a REST backend (currently Express) that
validates identity, validates uploads, stores metadata in MongoDB, stores files
on disk, and returns controlled responses. The frontend renders outcomes with
clear loading/error feedback. This architecture is modular, explainable, and
clinically relevant, with a clear path to production-level hardening.
